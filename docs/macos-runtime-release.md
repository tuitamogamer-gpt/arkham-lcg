# Preparing the Apple Silicon runtime archive

The existing native builder applies `codesign --sign -`. This is **ad-hoc installation signing**: macOS can verify the binary's integrity locally. It is not an Apple Developer ID signature, notarization, or a claim that Gatekeeper trusts an Internet download. This export route keeps those meanings separate and preserves the ordinary runtime capability checks.

The [macOS workflow](../.github/workflows/macos-runtime.yml) runs for relevant native source, packaging and workflow changes pushed to `main`, or by manual dispatch. It builds the complete Barkham, Epic Labyrinth and Epic Machinations aggregate on actual macOS ARM64, rebuilds the upstream frontend, executes the current full native test driver, and prepares a candidate without replacing an installed runtime or starting PostgreSQL. The workflow downloads the exact checksum-pinned `v20260904.1` base distribution directly; it does not start the companion merely to install its libraries. Pushes use the hosted runner; manual dispatch also offers a preexisting self-hosted runner.

GitHub's [current hosted runner table](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) lists `macos-15` as an ARM64 M1 runner. Its standard 7 GiB memory and 14 GiB storage impose a real limit on this cold build. The workflow verifies actual `uname` and Node architecture, checks initial resources, and keeps the existing 2 GiB reserve during every native build command. Initial resource checks do not promise the complete build fits. A reserve stop or timeout produces evidence, not a completed package. For more headroom, select `self-hosted`; that requires an already registered runner with `self-hosted`, `macOS`, `ARM64` labels, Xcode command-line tools, Node tooling, `pkg-config` and GMP. At least 16 GiB RAM and 24 GiB initially free storage are recommended. This repository does not configure such a runner.

The Linux workspace cannot execute macOS signing or this archive's native programs; the GitHub hosted workflow is a separate Mac execution route. As of this preparation, the GitHub credential can read normal repository/workflow metadata, but requests to list repository Actions secrets, variables and self-hosted runners return HTTP 403. No Apple signing identity, notarization credential or self-hosted runner is asserted to exist. Preparing these files alone does not execute the workflow.

The [first actual hosted ARM64 attempt](https://github.com/tuitamogamer-gpt/arkham-lcg/actions/runs/37744018748) on 8 October passed architecture, resources, GMP and the pinned base checksum, then failed while compiling PostgreSQL 14.15. Its configure probe found the host's `strchrnul`, introduced in macOS 15.4, while the compiler targeted macOS 15.0. The private bootstrap now selects PostgreSQL's existing local fallback and renames it after the SDK includes to avoid the newer SDK declaration. This macOS-only compatibility patch preserves compiler warnings and the deployment target; Linux source and settings stay unchanged. A conflicting unavailable-declaration compile/run test and an isolated build of the actual pinned PostgreSQL source pass on Linux. Those diagnostics do not constitute successful Mac execution. The original failed logs and evidence artifact remain retained, and the full Mac aggregate/archive still require a successful retry.

The [separately verified ARM64 retry](https://github.com/tuitamogamer-gpt/arkham-lcg/actions/runs/37759826893) at commit `4fa979e` passed its compiler/PostgreSQL bootstrap, full Haskell dependency build, and actual complete **232-example native suite with zero failures** on 8 October. The recorded extension source hash remains `4088f4badb00f37a9e3a77680698cd2b1872469b1796c70b82e2a3dd0a2d1cd3`; the tested Mac engine hash is `6fd04ba79e6cbab8b4b0a9c233391f2d0dc20721314d7a4b831ab738695ced84`. The native result explicitly records a sanitized test environment and the unchanged full driver. Subsequent candidate preparation failed with `Unexpected Mach-O libpq registration.` PostgreSQL's actual hosted install name was under `/Users/runner/work/_temp`, outside the old rewriter's temporary prefixes. The workflow did not export a completed package. This passing Mac native test result is distinct from archive, installation and gameplay acceptance.

Candidate relocation now uses the exact configured PostgreSQL library path and its canonical toolchain alias, with the explicit `@rpath/libpq.5.dylib` form. Known private build roots bound RPATH changes; arbitrary runner or temporary prefixes are not accepted. Every Mach-O command, library match and fixed-size replacement slot is validated before writing. Actual `otool` output and the candidate's pre-edit SHA are retained before relocation, including on a later failure. Synthetic malformed-header and checksum-pinned real-header regressions do not replace an actual Mac export result. `--bootstrap-only` remains an isolated toolchain stage without scenario source, a runtime candidate or behavior-evidence replacement.

After an actual successful `--with-epic-machinations --test --prepare-only` build, the [export helper](../scripts/package-macos-runtime.mjs) accepts the candidate, its matching full behavior proof and the original base archive:

```sh
node scripts/package-macos-runtime.mjs \
  --candidate /path/to/derived-runtime/.candidate-123 \
  --proof output/rules-server/rules-behavior-tests.json \
  --base-archive /path/to/ArkhamHorror-macos-arm64-v20260904.1.tar.gz \
  --output output/macos-runtime \
  --source-epoch "$(git show -s --format=%ct HEAD)"
```

The output directory must not already exist. The helper verifies the current extension hashes, exact API/frontend/presentation identity and unfiltered full test driver. It accepts the actual passing example count rather than assuming an older count. It copies only the API, frontend, presentation and manifest from the candidate. Every selected candidate input and its parent components must be actual files/directories, and any nested frontend link must stay inside that validated frontend subtree; a link into the candidate's private `config` or saved-game data fails export. Libraries, PostgreSQL executables/extensions/share files and `data/setup.sql` come from a fresh extraction of the SHA-256-verified base archive. Only those explicit immutable base roots are authorized for cross-library links. The export creates an empty private `config` directory. Existing session keys, database clusters, logs, backups and saved games are excluded.

Every Mach-O file must be thin ARM64. A read-only Linux check of the actual checksum-matched base archive found 54 thin ARM64 Mach-O dependency files, with absolute PostgreSQL imports pointing into the original upstream GitHub runner's build directory. These public pinned dependency prefixes alone are rewritten to existing `@loader_path` paths in the isolated export; unknown non-system imports still fail. The helper distinguishes actual load imports from a dylib's own install ID and requires canonical install-ID targets to exist as ARM64 Mach-O files in the same exported directory. The base includes separately signed unversioned PostgreSQL copies whose signature containers differ from versioned files; both originals remain bound to the verified archive, and the export records their original hashes. AppleDouble/`.DS_Store` metadata is discarded. This header inspection is not macOS execution or signature verification.

The API keeps its already verified ad-hoc signature and its tested binary hash; distribution dependencies receive ad-hoc signatures after their isolated relocation. The helper checks strict signatures and that non-system dynamic imports can resolve inside the exported runtime, then rechecks the derived manifest. It creates `Chronicle-rules-macos-arm64.tar.gz`, `SHA256SUMS`, the unchanged native behavior report and a `chronicle-package.json` inventory with every runtime file's SHA-256 and size, including the exact dependency relocation edits. File times use the supplied source epoch, archive ownership is normalized, and gzip omits a wall-clock header; byte identity still depends on the supplied candidate, frontend, base archive and actual proof bytes.

The package record explicitly reports `developerIdSigned: false`, `notarized: false`, `installed: false`, `gameplayCertified: false`, `savesIncluded: false` and `sessionKeysIncluded: false`. A failure removes any purported completed archive/metadata and retains a false failure report. The workflow uploads a completed archive only after all commands succeed; it creates no GitHub Release, tags or installed runtime.

Use the existing companion with `ARKHAM_RULES_RUNTIME` pointing to the extracted `game` directory for an isolated macOS acceptance run. Native API, three-group browser/Ready behavior, saved-game persistence through a managed restart and scenario completion remain separate checks. A static Vercel client deployment does not install or host this runtime. Preparing this pipeline does not turn the existing Linux acceptance into a macOS result.

Trusted public macOS distribution needs a separate Developer ID Application certificate and its private key in an isolated signing keychain, plus an Apple notarization credential (App Store Connect API key or an app-specific password with Team ID). Signing would change API bytes and must produce explicitly bound signed-artifact provenance while preserving the original tested native hash. Successful `notarytool` submission and archive assessment must be recorded before claiming notarization; no such credential-dependent route is implemented or claimed here.
